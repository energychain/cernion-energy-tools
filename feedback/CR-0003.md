## 1. DELETE-Endpunkte für alle vier Agenten

### Problem

Keiner der vier Agenten hat einen DELETE-Endpunkt:

| Agent | Fehlender Endpunkt |
|-------|--------------------|
| mastr-quality | `DELETE /api/mastr-quality/audits/:id` |
| grid-connection | `DELETE /api/grid-connection/validations/:id` |
| energy-sharing | `DELETE /api/energy-sharing/validations/:id` |
| redispatch-expost | `DELETE /api/redispatch/audits/:id` |

### Referenz-Implementierung

`energy-sharing-allocation` hat bereits ein funktionsfähiges Soft-Delete-Pattern:

```js
// services/energy-sharing-allocation.service.js
remove: {
  rest: 'DELETE /allocations/:id',
  async handler(ctx) {
    const doc = await this.db.get(ctx.params.id);
    await this.db.put({ ...doc, status: 'deleted', deletedAt: new Date().toISOString() });
    return { success: true, id: ctx.params.id };
  }
}
```

### Erwartetes Verhalten

- HTTP 200 mit `{ success: true, id }` bei Erfolg
- HTTP 404 wenn die ID nicht existiert
- **Soft-delete**: Setzt `status: 'deleted'` + `deletedAt` im PouchDB-Dokument
- `list`-Endpunkte MÜSSEN gelöschte Dokumente standardmäßig ausblenden (`status !== 'deleted'`)
- Optional: Query-Param `?includeDeleted=true` für Admin-Ansicht

### UI-Auswirkung

Alle vier Agenten-Seiten sollen nach Abschluss einer Validierung/Prüfung die Möglichkeit
haben, alte Datensätze zu löschen (Confirmation Dialog → DELETE-Call).

## 2. Curtailment-Quellenangabe und High-Frequency-Flag (redispatch-expost)

### Problem

Step 4 (`curtailmentCorrelation`) berechnet Abregelungsdaten intern, exponiert aber
weder die Datenquelle (`source`) noch einen direkten `highFrequencyFlag` als top-level
Response-Felder. Der alte Contract hatte:

```json
"curtailment": {
  "totalGWh":          123.4,
  "source":            "netztransparenz",
  "highFrequencyFlag": false
}
```

### Ist-Zustand (v0.20.x)

- `curtailmentGWh` ist in `riskAssessment.curtailmentGWh` verfügbar
- High-frequency-Erkennung existiert als Finding-Code `RD_HIGH_CURTAILMENT_PERIOD`
- Quellenangabe (`netztransparenz.de` vs. Datapoint-Fallback) ist **nicht** im Response

### Gewünschter Soll-Zustand

Neues top-level Objekt `curtailment` in der redispatch-expost Audit-Response:

```json
"curtailment": {
  "totalGWh":          123.4,
  "source":            "netztransparenz" | "datapoint" | "none",
  "highFrequencyFlag": false
}
```

`highFrequencyFlag: true` wenn Finding `RD_HIGH_CURTAILMENT_PERIOD` in `findings[]`.
`source` aus dem Step-4-Kontext ableiten (Weg A = `"netztransparenz"`, Weg B = `"datapoint"`).

### Implementierungsaufwand

**Gering** — Step 4 kennt die Quelle bereits intern. Nur das Mapping ins Return-Objekt fehlt.

## 3. Portfolio Weg A / Weg B als direktes Response-Feld (redispatch-expost)

### Problem

Der alte Contract hatte `portfolio.weg: "A" | "B"` als direktes Response-Feld.
Aktuell kann Weg B nur über das Finding `RD_USED_WEG_B` in `findings[]` erschlossen werden.

### Ist-Zustand (v0.20.x)

```js
// Weg B wird in tryDatapointFallback() gesetzt und als Finding gespeichert
// Kein direktes portfolio.weg Feld im Response
```

### Gewünschter Soll-Zustand

Erweiterung des `summary`-Objekts (oder neues `portfolio`-Objekt):

```json
"summary": {
  "totalInstallations": 59,
  "portfolioSource":    "weg_a" | "weg_b",
  "findingsCount": { ... },
  "skippedSteps":  [],
  "durationMs":    45230
}
```

Alternativ als separates Feld auf Root-Ebene: `"portfolioSource": "weg_a"`.

### Implementierungsaufwand

**Gering** — `tryDatapointFallback()` kennt `usedWegB`. Rückgabe erweitern:
```js
return { success: true, id, portfolioSource: usedWegB ? 'weg_b' : 'weg_a', ...report };
```
