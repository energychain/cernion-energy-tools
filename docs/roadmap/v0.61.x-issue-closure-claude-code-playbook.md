# v0.61.x Issue Closure Playbook for Claude Code

Stand: 2026-06-09

## Ziel

Alle aktuell offenen Issues in `energychain/cernion-energy-tools` sollen im Release-Zweig `v0.61.x` bewertet und geschlossen werden, damit danach ein offizieller Feature Freeze erfolgen kann.

Dieses Playbook beschreibt den Arbeitsmodus fuer Claude Code. Es ist bewusst als Gate-Prozess formuliert: nicht jedes Issue darf automatisch implementiert werden.

## Arbeitsmodell

Claude Code arbeitet pro Issue isoliert:

1. Frischen Branch oder Worktree von sauberem `main`/`v0.61.x` erstellen.
2. Issue inklusive Kommentare lesen.
3. Issue klassifizieren:
   - `implementable`: klarer Scope, Plattformlogik passt, testbar.
   - `needs-product-cut`: fachlich sinnvoll, aber fuer Code zu breit; erst Minimalinkrement definieren.
   - `architecture-risk`: wuerde Layering, Routing, Trust Boundary, Receipt-/Evidence-Logik oder bestehende Agentenlogik veraendern.
   - `duplicate-or-superseded`: schliessen oder mit anderem Issue zusammenfuehren.
4. Bei `architecture-risk` oder unklarem Produktzuschnitt: nicht implementieren. Stattdessen einen Issue-Kommentar mit Einordnung, Risiko und vorgeschlagenem v0.61.x-Minimalscope vorbereiten.
5. Bei `implementable`: GitNexus-Kontext und Impact-Analyse fuer betroffene Symbole ausfuehren, dann implementieren.
6. Tests laufen lassen:
   - engster passender Jest-Test
   - ggf. `npm run test:unit:ci`
   - bei API-/Service-Aenderungen `npm run audit:openapi` und `npm run check:llm`
   - vor Release-Kandidaten `npm run release:check`
7. PR/Commit mit `Closes #NNN` vorbereiten.
8. Issue erst schliessen, wenn Merge/Commit in `v0.61.x` gelandet ist und Verifikation dokumentiert wurde.

## Plattformlogik-Risiko-Gates

Claude Code muss stoppen und kommentieren, wenn eine Umsetzung:

- deterministische Receipt-/Evidence-Ketten durch LLM-Synthese ersetzt,
- `scope-blocked`, Tenant-, Actor- oder Purpose-Gates lockert,
- bestehende Blueprint-/Policy-Auswahl implizit ueberschreibt,
- neue Prozesslogik ohne klare Service-Grenze quer in `personal-agent` oder Routing-Logik einbaut,
- regulatorische Bewertung als harte Wahrheit statt als plausibilisierte Entscheidungshilfe ausgibt,
- fuer ein Discovery-Issue sofort ein grosses Cockpit oder eine neue Engine baut, obwohl ein kleiner Datenvertrag/Pruefpunkt reicht.

## Claude-Code Prompt-Schablone

```text
@workspace

Bitte bearbeite GitHub Issue #NNN fuer cernion-energy-tools im Zielrelease v0.61.x.

Vorgehen:
1. Lies das Issue und alle Kommentare mit gh.
2. Ordne es ein: implementable, needs-product-cut, architecture-risk oder duplicate-or-superseded.
3. Lies die relevanten Repo-Regeln in AGENTS.md und CLAUDE.md.
4. Suche den passenden Codepfad. Nutze GitNexus fuer Kontext und fuehre vor jeder Symbolaenderung eine Impact-Analyse aus.
5. Wenn das Risiko fuer Plattformlogik, Layering, Tenant/User/Purpose-Gates, Receipt/Evidence-Ketten oder Routing-Policies hoch ist: nicht implementieren. Formuliere stattdessen einen Issue-Kommentar mit Risiko, Begruendung und v0.61.x-Minimalscope.
6. Wenn implementierbar: setze das kleinste sinnvolle Inkrement um, mit Tests und Dokumentation.
7. Verifikation: Fuehre den engsten passenden Test aus. Bei Service/API-Aenderungen zusaetzlich audit:openapi und check:llm. Wenn das Issue releasekritisch ist, release:check.
8. Liefere am Ende: Klassifikation, geaenderte Dateien, Tests, Restrisiko und ob das Issue per Commit/PR geschlossen werden kann.

Nicht-Ziele:
- Keine grossen Architektur-Rewrites.
- Keine stillen Aenderungen an Auth-, Tenant-, Actor-, Purpose- oder Receipt-Logik ohne explizite Risikoentscheidung.
- Keine externen Aktionen ausser GitHub-Kommentar/PR/Issue-Schluss, wenn dafuer Freigabe erteilt wurde.
```

## Definition of Done fuer v0.61.x

- Jedes aktuell offene Issue ist entweder implementiert, sauber zusammengefuehrt oder mit dokumentierter Architektur-/Produktentscheidung geschlossen.
- `package.json` steht auf einer `0.61.x` Version.
- `CHANGELOG.md` oder Release Notes dokumentieren die geschlossenen Klassen.
- `npm run release:check` laeuft fuer den finalen Release-Kandidaten.
- Danach wird ein Feature Freeze ausgerufen: nur noch Bugfixes, Tests, Release Notes und Sicherheitskorrekturen.
