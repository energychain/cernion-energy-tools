## Vorgehen pro Issue

1. Lies das Issue und alle Kommentare:

   ```bash
   gh issue view NNN --repo energychain/cernion-energy-tools --comments
   ```

2. Lies die lokalen Repo-Regeln:

   ```bash
   sed -n '1,220p' AGENTS.md
   sed -n '1,220p' CLAUDE.md
   ```

3. Klassifiziere vor Code:

   - `implementable`: klein genug und testbar.
   - `architecture-risk`: erst Plan/Risikokommentar, keine Implementierung ohne explizite Entscheidung.
   - `needs-product-cut`: Minimalinkrement fehlt.

4. Nutze GitNexus vor Symbolaenderungen. Bei HIGH/CRITICAL Impact: stoppen und Risiko dokumentieren.

5. Implementiere nur das kleinste v0.61.x-Inkrement, das das Issue belastbar schliesst.

6. Tests:

   - Engsten passenden Jest-Test ausfuehren.
   - Bei Personal-Agent-/Routing-/Receipt-Logik passende Regressionstests ergaenzen.
   - Bei API-Aenderungen `npm run audit:openapi` und `npm run check:llm`.
   - Vor Abschluss der Release-blocker mindestens `npm run test:unit:ci`.

7. Abschluss:

   - Ergebnis mit geaenderten Dateien, Tests und Restrisiko dokumentieren.
   - Commit/PR mit `Closes #NNN`.
   - Issue erst nach Merge/Commit in `v0.61.x` schliessen.

## Harte Stop-Kriterien

Nicht implementieren, sondern Plan/Risikokommentar vorbereiten, wenn die Aenderung:

- Tenant-, User-, Actor-, Scope- oder Purpose-Gates lockert,
- Receipt-/Evidence-Grounding durch ungebundene LLM-Synthese ersetzt,
- bestehende Blueprint-/Routing-Policy implizit ueberschreibt,
- mehrere Agentenpfade zusammenlegt, ohne dass die Plattformlogik klar bleibt,
- Security- oder Wallet-Key-Material ohne sauberes Threat Model verarbeitet.
