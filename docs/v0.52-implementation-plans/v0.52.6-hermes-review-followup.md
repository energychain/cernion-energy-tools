# Cernion v0.52.6 — Hermes Review Follow-Up Findings (Part 3)

**Meilenstein:** v0.52.7 (oder nächster Patch)
**Scope:** Residual Bugs, Race Conditions, Security Risks und API-Contract-Flaws aus dem Hermes Review der v0.52.6 Changes.
**Ziel:** Behebung der 5 verbleibenden High-Impact-Findings durch CoPilot.

---

## Finding 1 — Security: Sensitive Request Headers Persisted in Dream Job Payload

**Dateien:** `services/personal-agent.service.js:buildDreamAuthMeta()` / `src/personal-agent-dreamer.js:scheduleDream()`

**Problem:** `buildDreamAuthMeta` kopiert das gesamte `requestHeaders`-Objekt (potentiell `Authorization`, `Cookie`, Bearer-Tokens) in `authMeta`. Dieses `authMeta` landet serialisiert im durable Dream Job Record auf Disk. Das überschreitet die angeforderte Rekonstruktion von Roles/Scopes/Tenant und schafft ein Information-Disclosure-Risiko bei langlebigen Job-Dateien.

**Fix:** Entferne `requestHeaders` aus `authMeta`. Falls tracing-relevante Header (z.B. `x-request-id`) benötigt werden, whiteliste explizit nur nicht-sensitive Keys.

---

## Finding 2 — API Contract Flaw: `object-store.put` Strips `_rev` on Success

**Datei:** `services/object-store.service.js:put` Handler

**Problem:** Nach erfolgreichem `this.db.put(doc)` returned der Handler `toPublic(doc)`, das `_rev` entfernt. Weil `get` in v0.52.6 modifiziert wurde, um `_rev` zurückzugeben, muss ein Client, der chained CAS Updates macht, einen extra `get` absetzen, um die neue Revision zu erhalten. Die Response ist intern inkonsistent.

**Fix:** Füge `_rev: doc._rev` in den Success-Return des `put` Handlers ein (analog zum `get` Handler).

---

## Finding 3 — Logic Bug: Explicit `_rev: undefined` Causes Spurious 409 on Existing Documents

**Datei:** `services/object-store.service.js:put` Handler

**Problem:** Wenn `_rev: undefined` explizit übergeben wird, überspringt der 404-Branch die Validierung (`requestedRev !== undefined`), aber der Existing-Document-Branch evaluiert `undefined !== existing._rev` (immer `true`) und wirft `OBJECT_OCC_CONFLICT`. Das bricht optional/dynamisches Parameter-Forwarding.

**Fix:** Normalisiere `requestedRev` vor der Prüfung: treat `undefined` und `null` identisch als „kein CAS“, oder prüfe im Existing-Document-Branch auf `hasRevToken && requestedRev !== undefined`.

---

## Finding 4 — Error Fidelity: `db.put` OCC Conflict Hides Actual Current Revision

**Datei:** `services/object-store.service.js:put` Handler

**Problem:** Wenn `this.db.put(doc)` einen 409 wirft, reported der Catch-Block `currentRev: null` im Error-Data, obwohl `rev` aus `existing._rev` bereits weiter oben im Handler befüllt wurde. Retry-Logik verliert die aktuelle Revision, die sie für den nächsten Versuch braucht.

**Fix:** Setze im Catch-Block für `db.put` 409-Fehler `currentRev` auf `existing._rev` (bzw. den zuvor gelesenen `rev`-Wert), nicht auf `null`.

---

## Finding 5 — Inconsistent Guard: Empty-String `_rev` Treated Differently on Create vs Update

**Datei:** `services/object-store.service.js:put` Handler

**Problem:** `_rev: ''` gegen ein nicht-existierendes Dokument bypassed CAS (kein 409 im 404-Branch), aber gegen ein existierendes Dokument triggert es 409 (`'' !== '1-...'`). Die asymmetrische Behandlung macht den Empty-String-Sentinel unzuverlässig.

**Fix:** Einheitliche Semantik: `_rev: ''` sollte entweder (a) wie `null`/`undefined` als „kein CAS“ behandelt werden, oder (b) konsistent in beiden Branchen einen 409 auslösen. Empfohlen: Option (a), leere Strings als „kein CAS“ normalisieren.
