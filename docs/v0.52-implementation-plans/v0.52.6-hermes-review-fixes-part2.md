# Cernion v0.52.6 — Hermes Code Review Fixes (Part 2)

**Meilenstein:** v0.52.6
**Scope:** Verbleibende Architektur-, Security- und Race-Condition-Fixes aus dem zweiten Hermes Code Review.
**Ziel:** Behebung von Stale-State, unvollständigem OCC, Race Conditions und Meta-Overrides.

## Findings zur sofortigen Behebung durch CoPilot

Der lokale *Hermes Agent* hat das Diff der v0.52.5 geprüft und festgestellt, dass einige Probleme noch existieren oder unvollständig gelöst wurden.
**Bitte setze exakt diese 5 Fixes im Rahmen des v0.52.6 Releases um:**

### 1. Stale Session Snapshot in Durable Job Payload
**Datei:** `src/personal-agent-dreamer.js:scheduleDream()` / `services/personal-agent.service.js:runDream()`
**Problem:** Der Dream-Job speichert das komplette `session`-Objekt beim Scheduling in seiner Payload. Wenn er 5+ Minuten später aufwacht, ist dieses Objekt veraltet (Stale Data), falls es in der Zwischenzeit andere Updates gab.
**Fix:** Speichere in der Job-Payload nur noch die `sessionId` (und ggf. die `tenantId`). Der Worker muss beim Aufwachen in `runDream()` die aktuellste Session zwingend frisch aus dem Object-Store laden.

### 2. OCC Fix Incomplete — Native CAS/_rev Not Used
**Datei:** `src/personal-agent-dreamer.js:enrichL2Profile()`
**Problem:** In v0.52.5 wurde nur der manuelle `updatedAt` Recheck verschoben. Es gibt aber weiterhin ein TOCTOU-Fenster (Time-of-check to time-of-use) zwischen dem Read und dem Recheck.
**Fix:** Verwende die native Compare-And-Swap (CAS) Mechanik der zugrundeliegenden Datenbank (z.B. durch Mitgeben der `_rev` ID im `object-store.put`). Entferne den doppelten `updatedAt`-Read und fange stattdessen saubere Revisions-Konflikte im Fehlerpfad des `put` ab, um den Retry auszulösen.

### 3. Generation Bump Race on Concurrent Re-schedule
**Datei:** `src/personal-agent-dreamer.js:scheduleDream()`
**Problem:** Die Job-Generation wird im "Read-Modify-Write"-Stil inkrementiert. Bei zeitgleichen Reschedules aus mehreren Node-Instanzen wird dieselbe Generation mehrfach berechnet, was zu überschriebenen oder ignorierten Dream-Jobs führt.
**Fix:** Nutze auch hier die native Optimistic Concurrency des `job-store.js`. Alternativ: Ersetze das applikative `generation`-Feld durch eine strikte Abhängigkeit von der nativen Datenbank-Revision (`_rev`) des Job-Records.

### 4. Unbounded Job Store Growth / Missing GC
**Datei:** `src/personal-agent-dreamer.js` / `src/job-store.js`
**Problem:** Jeder Chat erzeugt oder storniert langlebige Job-Einträge. Wenn Jobs in Status `completed`, `canceled` oder `failed` enden, verbleiben sie ewig im Store. Die Abfragen (`findJobByIdempotencyKey`) werden linear langsamer.
**Fix:** Implementiere eine Garbage Collection (GC) Strategie. Abgeschlossene/Abgebrochene Jobs im Dreamer-Umfeld müssen entweder direkt nach Ausführung gelöscht (oder über eine TTL-Mechanik im Store automatisch bereinigt) werden.

### 5. dreamCtx Auth Under-Specification & Meta Override
**Datei:** `services/personal-agent.service.js:runDream()`
**Problem:** Der neu geschaffene `dreamCtx` erhält nur `{ userId }`. Dadurch gehen alle Rollen, Scopes und Berechtigungen des ursprünglichen Requests verloren, was bei Downstream-Aufrufen zu Auth-Fehlern führt. Zudem überschreibt der Aufruf das komplette `options.meta` Objekt, statt es zu mergen, was Tracing-Daten vernichtet.
**Fix:** Beim Erzeugen des `dreamCtx` müssen relevante Auth-Informationen (Roles, Scopes, Tenant) aus der Job-Payload rekonstruiert oder in den Context übernommen werden. `options.meta` muss per Deep Merge (z.B. `{ ...currentMeta, ...newMeta }`) ergänzt statt überschrieben werden.

## Abschluss
Erstelle für diese Fixes das Release **v0.52.6** und sorge dafür, dass alle bestehenden Tests grün bleiben.
